Sentinel CI

A self healing CI agent.

When a GitHub Actions run fails, SENTINEL CI reads the logs and the diff since the last green build, diagnoses the root cause, writes a minimal repair, and tries to break its own fix before a pull request opens. It is the SENTINEL six agent architecture pointed at CI pipelines. The engineering is in the brakes.

A failed run, as the parser sees it

Stage 1 is built and tested today: the watcher spots the failed run, and the log parser reduces a full Actions log to the few facts diagnosis needs. This is the parser's real output shape on a sample pytest failure.

The six agents

Every agent reads and writes one typed incident state, so each conclusion traces back to its evidence.

AgentJobStatus
01 Mission Controller Opens the incident, owns routing, opens the PR or escalates Stage 1 live
02 Codebase Analyst Fetches the diff since the last green build, maps blast radius Stage 2
03 Failure Hypothesis Ranked candidate causes, each with the observation that would kill it Stage 2
04 Root Cause Tests hypotheses until one cause explains every symptom Stage 2
05 Repair Drafts the smallest safe fix, with a rollback path Stage 2
06 Adversarial Verification Reruns the failing tests plus the regression suite in Docker and argues against the fix Stage 3

The verification gate

A repair becomes a pull request only if all three hold:

  1. The originally failing tests pass with the patch applied.
  2. The regression suite passes in a clean Docker environment.
  3. The verification agent's challenge (wrong layer, masked symptom, new breakage) fails to break the fix.

Anything else loops back to Repair with the verifier's notes, a capped number of times, and then escalates to a human with the full evidence trail. SENTINEL CI never auto merges.

One workflow file, plus a free Google AI Studio key as a repository secret. SENTINEL CI runs on free tiers only: Gemini free tier, GitHub free, Actions free minutes, Vercel free for this page.
